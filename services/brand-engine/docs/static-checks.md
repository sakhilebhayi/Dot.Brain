# Built-in static checks

Code: [`src/analyze/checks/`](../src/analyze/checks/). Tests: [`test/checks/`](../test/checks/).

Nineteen of the thirty-seven automated checks in the BXQS rubric (`brand/rubrics/bxqs-1.0.0.json`) can be run by
reading a checkout. `src/analyze/checks/` holds them: one module per check, no network, no browser, no model, no clock, no
environment, and **read-only over the checkout**. They plug into the analyzer
([ADR-0021](../../../adr/ADR-0021-brand-feeling-engine.md), [ADR-0022](../../../adr/ADR-0022-bxqs-scoring-policy.md))
and produce exactly the evidence the scoring engine reads: a value from 0 to 1 per rubric check id, and findings.

They measure what the files say. They do not render a page, run a test, call a service or judge a person, and
where they cannot tell, they say `not_measured` and give a reason. **Nothing here produces a pass where nothing
was measured.**

## The contract

The registry in `src/analyze/registry.js` ([README, "The check registry and the file API"](../README.md#the-check-registry-and-the-file-api)) loads each module in its own worker thread and validates what comes back (`src/analyze/check-shape.js`). Each file `<check-id with dots and underscores as dashes>.js` default-exports a frozen object:

```js
{ id, dimension, title, appliesTo(ctx) -> boolean, run(ctx) -> { status, evidence, findings } }
```

* `id` is a rubric check id (`d8.token_pair_contrast`); `dimension` is that check's rubric dimension id. A test checks both against the released rubric.
* `ctx` is read as `{ root, profile, files?, scope? }`. `root` is the absolute path of the checkout. `profile` is the resolved profile (`brand-engine profile resolve`) or `null`. `files` is the analyzer's read-only file API: **when it is present the checks list and read through it**, so the analysis report records what was declined (`coverage.skipped`), and every path it returns is re-validated; when it is absent or unusable (a direct call, a test, a provider that throws) they walk `root` themselves with the same rules. `ctx.scope` is the list of path prefixes from `analyze --scope` (empty means the whole checkout; see "Scope" below). `ctx.themes` is not used: the checks derive the themes from the stylesheets (light, and dark when the CSS has dark overrides). `ctx.options` is optional and used only by two checks (see "Defaults").
* `status` is `measured`, `not_applicable` (the repository has no such surface; for example Dot.Brain or a CLI has no templates or stylesheets) or `not_measured` (the surface exists but this check could not judge it). The analyzer rejects any other key in the result, so **the reason a check is `not_measured` travels as an info finding** with the rule `not-measured` and no location; a `not_applicable` result carries nothing.
* `evidence` is empty unless `measured`, then exactly one entry: `{ check_id, source_class: 'automated_check', result, detail, artifact_ref }`. `result` is a number from 0 to 1, higher is better, and becomes the evidence file's `automated[].value`. `detail` is at most 1,000 characters, states the counts behind the number and what was not looked at, and ends with a note when files could not be read (too large, minified, over the read budget).
* A finding is `{ id, severity, dimension, check_id, message, fix_hint, location?: { file, line }, kind?, wcag_level?, wcag_criterion? }`. `id` is `<check id>.<rule>.<nnn>` and unique. `location.file` is relative to the checkout. `severity` is `blocker`, `major`, `minor` or `info`. At most 1,500 findings are listed per check (the analyzer refuses 2,000); beyond that the most serious are kept and one info finding (`findings-truncated`) says how many were left out. The `result` always counts all of them.
* **`kind` (`wcag_failure` or `unsupported_claim`) is set only on blockers**, and a WCAG blocker carries `wcag_level` and `wcag_criterion`. It is what lets `evidence assemble` turn the finding into a score-capping blocker without guessing. A major or lower finding is a heuristic and never carries a kind, so it can never become a blocker downstream; `wcag_level` and `wcag_criterion` are also set, for information, on some non-blocking accessibility findings.
* Output is deterministic: files are visited in sorted order, findings are sorted by file, line and rule, and nothing depends on the clock, the path of the checkout or the order files were created in.

### How the output reaches the score

`analyze` copies `evidence[0]` into `analysis.json` (the file API and the worker are the analyzer's); `evidence assemble` writes it as `automated[]` and turns each blocker into an evidence finding (`unsupported_claim`, or `wcag_failure` with its level and criterion); `score` does the rest. `test/checks/integration.test.js` runs exactly that chain on the two fixture checkouts, with no mock.

### Scope

`analyze --scope <path-prefix[,..]>` sets `ctx.scope`. A scope limits the files a check **lists as a surface**: `repo.list()` in `_lib/repo.js` returns only the files at or under a prefix, so templates, stylesheets and language files are those of the surface. Everything that is an inventory of what exists rather than a judgement (`routes/*.php`, `app/` handlers, the view and page names for `d5.route_inventory_vs_claims`, the files "is this view mounted?" reads) goes through `repo.listAll()` and sees the whole checkout, and `exists()`/`read()` are never scoped. A link in an in-scope template is therefore resolved against the application's routes wherever they live, and a view in the scope that is mounted from outside it is still mounted. A scope with no UI file under it makes the UI checks `not_applicable`. Include the stylesheets a surface uses in its scope, or they are not judged.

### Not measured instead of a pass at 1.00

A share whose denominator is empty is `not_measured`, never 1.00: `d4.reduced_motion` with no motion declared, `d6.claim_lint` with no claim-bearing string, `d8.focus_visible` with no outline removal and no positive `tabindex`, and `d1.copy_profile_language_lint` with no banned phrase in the profile. The reason is the info finding `not-measured`, the score counts the check as zero and lists it, and a product that really has nothing to reduce or no claim earns no free points for it. (This is a judgement the owner can reverse for `d8.focus_visible` and `d4.reduced_motion`, where "nothing found" is the good case; it is made here because a 1.00 from nothing was reported as a vacuous pass.)

### Mounted and unmounted templates

`_lib/views.js` answers "does anything render this Blade view?" textually, from the roots (every string literal in non-component PHP that is a view name, `Foo::class` and Livewire names; `view()` calls) along the edges of mounted templates (`@include`, `@extends`, `@each`, `@component`, `<x-name>`, `<livewire:name>`, `@livewire`) and of mounted component classes (`app/Livewire`, `app/View/Components`). A class-based component's views count only if the component is mounted. Framework conventions (`errors.*`, and with Jetstream, Breeze, Fortify, Livewire or Folio installed their own conventional views) are never unmounted. When the answer cannot be known (`view($variable)`, `<x-dynamic-component>`, `<livewire:is>`, a dynamic prefix that covers the view, or no PHP at all) the template is treated as mounted. Today only `d8.labels_alt_lang` uses it, to turn a blocker in a provably unmounted template into a major with a note: a blocker caps a dimension, and a file nobody renders should not.

### Defaults that are not the profile's

The profile has no field for a navigation depth or a field-count bound, so `d3.nav_depth` uses 3 levels and `d3.field_counts` uses 8 fields unless the caller passes `ctx.options.nav_depth_bound` or `ctx.options.max_fields_per_form`. The `detail` says which one was used ("engine default bound" or "bound supplied by the caller"). `d2.font_palette_deny_list` combines the profile's `visual_direction.prohibited` entries (matched by font name, whole word, and by hex value) with a short built-in list of fonts that arrive as a browser, OS or starter-kit default (`GENERIC_FONTS` in the module): Arial, Helvetica, Times, Courier, Verdana, Tahoma, Trebuchet MS, Segoe UI, Roboto, Inter, Open Sans, Lato, Montserrat, Poppins, Figtree, Instrument Sans and Nunito. That list is a judgement and a one-line edit.

## What is deliberately not built

These rubric checks need something a read of the checkout cannot give. They are listed in `_lib/skipped.js` with their reasons, and a test requires that every automated check in the rubric is either built or listed there. They are for the adapters (an external report) or a later increment.

## How the rubric's words were read

* **Both themes.** Light is `:root`, `html`, `body` and `*` declarations; dark is `@media (prefers-color-scheme: dark)`, `[data-theme=dark]`, `[data-bs-theme=dark]`, `.dark` and the like (a `:not([data-theme="light"])` marker does not make a selector a light theme). A theme overlay applies on top of the base. If no dark overrides exist, only light is evaluated and the detail says so.
* **Pairs.** A pair is only something the code declares or names: a rule that sets `color` and `background` (one colour for both, a drawn dot or bar, is not a pair); a DESIGN.md front-matter component with `backgroundColor` and `textColor`; `X` and `X-ink`, `X-foreground`, `X-fg`, `on-X`; a plain text token (`--text`, `--muted`, ...) that a rule really uses as `color`, on a page-level ground or panel token (`--bg`, `--panel`, `--surface`, `--card`, `--sunken`, ...; component tokens such as `--input-bg` are not grounds); and a focus indicator (a `--focus`/`--ring` token, or the colour of an `outline` in a `:focus` rule) against those grounds at 3:1 (WCAG 1.4.11). **Each stylesheet is its own palette**: a token a file declares wins over the same name in another file, and tokens are only paired with tokens declared in the same file, so two unrelated CSS files that both define `--bg` are not mixed. A pair reached from several sources is reported once, under the strongest. Large text is 24px, or 18.66px and bold. Ratios are compared unrounded and shown truncated, so 4.4999 is never displayed as 4.50.
* **Blocker or major.** A finding is a blocker when the evidence in the file is a definite failure of a level A or AA criterion (an `<img>` with no `alt`, no `lang`, zoom disabled, a declared pair below its threshold) or a claim the profile's policy and the rubric's `unsupported_claim` describe (an invented count, a compliance or licensing claim, a guarantee, a returns claim). Everything that depends on something the check cannot see (a label that may live in another file, a pair that is only paired by name) is a major or lower, and carries no `kind`.
* **Claims policy.** `claims_policy` rules are prose. The check ties each pattern family to the policy rules that mention its subject (by keyword) and names them in the message; severity does not depend on that match. Rules that no pattern covers (for example "do not present estimates as certain") are counted and listed by id in the `detail` of `d6.claim_lint`: they need a person.
* **Evidence markers.** A claim is downgraded to `info` only when it sits under `data-evidence="<path>"` (on it or on an ancestor) or a `{{-- evidence: <path> --}}` / `<!-- evidence: <path> -->` comment on the same line or up to two lines above (in PHP language files, a `// evidence: <path>` comment on the same or the previous line), **and** the path names a file that exists inside the checkout. A missing file, a path that leaves the checkout and a URL (which cannot be verified offline) leave the finding at its full severity and say so.

## False-positive and false-negative limits

Read a finding as "look here", not as a verdict. What each check can get wrong:

* **All template checks.** Blade, Vue, Svelte, JSX/TSX and Twig are read by a small tolerant reader, not by their compilers. Dynamic fragments (`{{ }}`, `@if`, `<?php ?>`, JSX `{...}`) and components (`<x-...>`, `<Foo>`, `<livewire:...>`, anything with a hyphen) are opaque: an element that carries one is skipped, and what a component renders is never seen. Markup produced by JavaScript is never seen. In JSX, markup nested in a `{...}` expression (for example the body of a `.map()`) is opaque. Includes and layouts are not followed, except where a check says so (`d10.error_pages` follows `@include`/`@extends` two levels). `tests/`, `docs/`, `fixtures/`, `examples/`, `stubs/`, `vendor/` and `node_modules/` are not shipped surfaces and are skipped; a folder of saved third-party pages anywhere else is scanned as if it were the product.
* **`d8.token_pair_contrast`.** No cascade and no specificity: a pair in one rule may never be rendered together, and a pair rendered together through inheritance is not seen. A translucent background takes its colour from what is behind it, which a stylesheet does not say, so it is undetermined (counted in the detail, never as a pass). `color-mix()`, `lab()`, gradients, `currentColor` and unresolved `var()` are undetermined. Pairs named by convention (`major`) can be pairs nobody renders. Disabled states are exempt. A page with its own `<style>` keeps its tokens apart from the application's. Tailwind utility pairs (`bg-x text-y`), borders and per-component or per-`data-area` token overrides are not evaluated. `ink` and `text` can name a surface as easily as a foreground, so a plain text token is paired with grounds only when a rule uses it as a text colour. A focus ring is paired with the background behind it, read from the selector: an outline is drawn outside the border box, so the nearest ancestor named in the selector (`.top .search input:focus` looks at `.top .search`, then `.top`) that declares a `background` is the ground; only an inset ring (`outline-offset` below zero) sits on the element's own. A ring that belongs to no particular element (a bare `:focus-visible`, a tag, a ring token) could be drawn on any declared ground and is judged only if they all agree (all pass or all fail). A ring for a particular element (a class, an id, an attribute) with no ancestor background declared in its selector is **not measured**: the page ground is not assumed, and the detail counts them. A background that cannot be read (a gradient, an unresolved `var()`) leaves the pair undetermined. Backgrounds set by an element that is not named in the selector, inheritance, and a theme-specific override of an ancestor's background are not followed, so a ring that fails on a surround the stylesheet does not name is not found.
* **`d8.labels_alt_lang`.** The reachability of a template (above) is an approximation of the same kind: it is conservative, so "unmounted" is only said when nothing in the checkout names the view. A label supplied by another file or component is reported as missing (`control-no-label` is therefore a major, and files in `components/` directories and PascalCase Vue/JSX files are treated as fragments and skipped). A `<title>` set in a layout, `@inertiaHead`, `<Head>` or a layout component is recognised, but a title set any other way is reported as missing (major). Links and buttons whose name comes from CSS content are reported.
* **`d3.heading_structure`, `d3.nav_depth` and `d3.field_counts`.** Headings are judged per file: a layout (it has a slot or `@yield`) and a page that extends one and declares no `<h1>` are left out of the share, because the outline is split between files, and the detail counts them. Headings rendered by components are not seen. Navigation depth is the nesting of lists, `<details>` and dropdown containers inside `<nav>`; the number of clicks through pages to reach a destination needs a link graph that templates do not give, and a menu built by JavaScript is not seen. The bounds (3 levels, 8 fields) are defaults, not the profile's. A field is an input, select or textarea (radio groups count once, hidden fields and buttons not at all), or a component whose tag names one; a form assembled by a component is under-counted, and whether a field is needed is not measured.
* **`d8.focus_visible`.** Absence of a removed outline does not prove a visible indicator; it proves the browser default is not suppressed in the files read. A replacement is looked for in the same rule and in a `:focus`/`:focus-visible` rule for the same base selector only. Non-interactive focus targets (`main`, headings, `tabindex="-1"`) and the `:focus:not(:focus-visible)` pattern are not flagged.
* **`d4.reduced_motion`.** A single global override (a `*` or `html` rule in a reduced-motion query that zeroes durations) covers everything, as it does in a browser. Motion from JavaScript, SVG animation and video are not scanned. Every transition counts, not only movement.
* **`d4.spacing_type_scale_conformance`** and **`d9.token_usage_vs_profile`.** A scale is found by custom-property names (`--space-*`, `--spacing-*`, `--text-*`, `--font-size-*`) and DESIGN.md front matter; a scale with other names is not seen and the check is `not_measured`. A framework's default scale is not the product's. Only the first value of a shorthand is read for colour in some cases. Tailwind classes count as tokens only when the colour name is a theme colour (`--color-*` or `tailwind.config` `colors`); default-palette classes are counted as framework defaults. A `var()` of a name declared nowhere in the checkout is reported, but a token defined at run time is invisible.
* **`d2.font_palette_deny_list`.** By name only. The first family of a stack is the font; fonts loaded by JavaScript are not seen. The palette is checked only when the profile writes hex values in its prohibited list.
* **`d1.copy_profile_language_lint`** and **`d6.claim_lint`.** Patterns over text, in English only. They find "trusted by 5,000", "guaranteed returns", "ISO 27001", "bank-grade", "only 3 left" and the like; they do not understand context beyond a short look-back for limits ("up to 5 users") and negations ("no guarantee"). A figure that is true and sourced is flagged unless it carries an evidence marker. "The best" is flagged wherever it appears. Standards are flagged as certification claims only for the management-system numbers that are certified (ISO 9001, 14001, 27001, ...) or when a word such as "certified" or "compliant" is beside them, so "built against the ISO 15143-3 API" is not; "Win rate" as a metric label is reported (major) because a profile may forbid the wording, and it is not an unsupported claim until a person says so. Prices and plan limits can look like counts. A claim written in an image, in a PDF or by JavaScript is not seen. Strings from `lang/*.php` and JSON language files are read where they are plain string literals; strings built from variables are not.
* **`d6.privacy_terms_present`.** "Reachable from every public page" is approximated by a link in a layout, footer or shared partial. A page whose body is rendered from a database or a variable is not judged and earns no credit; a policy served from a CMS looks missing.
* **`d6.honest_states`.** Presence of wording only. It cannot say whether the wording is true or whether any data shown is real, so it never yields a value.
* **`d5.dead_links`.** Route names and paths are read from `routes/*.php` textually (groups with `prefix`/`name`, `resource`, `apiResource`, `view`, `match`, `redirect`, `fallback`). Routes registered by packages (Fortify, Jetstream, Livewire, Filament, ...), loops that build routes and controller-level logic are invisible (the one exception is Jetstream's terms and privacy pages, taken from `config/jetstream.php`): when the application installs a package known to register routes, unresolved auth-style names and paths are treated as unverifiable, not dead. Variables, built assets (`/build`, `/storage`), and client-side routers (Vue/React/Svelte) are counted as unverifiable and left out of the share. `@if (Route::has('x'))` guards are read from the Blade source: `&&` keeps the guard, `||`, a negation and the `@else` branch do not, and a block that is never closed guards nothing.
* **`d5.stubs_placeholders`.** "Coming soon" can be an honest label for a feature that is not built; it is a minor finding that still counts the surface. A TODO in a comment is info and does not count.
* **`d5.route_inventory_vs_claims`.** A keyword match between bullet points under a "Features"-style heading in README.md/PRODUCT.md and route, page or view names. A feature whose route is named differently looks unbuilt; a route that exists proves nothing about whether the feature works. Documentation that is out of date makes this noisy; the finding is minor.
* **`d10.error_pages`.** Presence and a link or button, not rendering or the status code. Laravel conventions are assumed when `resources/views` and `routes/` exist.
* **`d10.health_endpoint`.** Finds `/up`, `/health`, `/healthz`, `/status` and similar in `routes/*.php` and `bootstrap/app.php`. "It answers" is never credited. A failure path is recognised by a 5xx status, `abort()`, an exception handler or a dependency probe in the handler or its controller; a framework `/up` route counts as having one only when a `DiagnosingHealth` listener exists.

## Safety

* Every path is resolved against the real path of `ctx.root`. A file whose real path is outside it is not read; a symlinked directory is never entered; a symlinked file is followed only if it stays inside the root. `../x`, absolute paths and paths with NUL are refused. Tests cover all of these.
* Skipped: `.git/`, `vendor/`, `node_modules/`, `build/`, `dist/`, `out/`, `public/build`, `storage/`, `bootstrap/cache`, minified files (`*.min.*`, and stylesheets or HTML with a line over 10,000 characters), files over 1 MiB and files containing a NUL byte. At most 32 MiB are read in all, and a tree of more than 100,000 entries is cut short; when anything was not read, the evidence `detail` says so.
* No check writes, executes a program, opens a network connection, reads an environment variable or reads the clock. A test scans the sources for each of these and another proves the checkout is byte-for-byte unchanged after every check ran.
* A finding quotes the matched phrase and at most 40 characters either side. It never prints a whole line or a whole file, and no result contains the absolute path of the checkout.
* Hostile input (huge or unbalanced markup, nested braces, a route file that never closes) is bounded in time and does not throw. A 2,000-file checkout is analysed by all nineteen checks in about a second. Each check re-reads the tree in its own worker, which the analyzer's budgets allow.

## Tests

`node --test test/checks` from `services/brand-engine`. Fixtures are synthetic checkouts under `test/fixtures/checks/` (`good`: no finding from any check; `bad`: exact findings per check, with rule, severity, file and line) and temporary checkouts built inside the tests for boundaries (4.5 and 3.0 contrast, heading order, `alt=""`, evidence markers, dynamic fragments, `not_measured` instead of pass), path escape and symlinks, determinism and a 2,000-file performance check.
